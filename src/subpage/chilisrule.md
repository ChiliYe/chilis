## git提交规范

本项目采用 [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow) 管理分支，并使用 [Conventional Commits](https://www.conventionalcommits.org/) 规范提交信息。

### 分支管理

`main` 是始终保持可部署状态的主分支。日常开发在从 `main` 创建的短期分支上进行，通过 PR 审查后合并回 `main`。

分支应使用小写字母，并以类别和简短描述命名：

| 类别      | 用途                                                               | 示例                   |
| :-------- | :----------------------------------------------------------------- | :--------------------- |
| `feat/`   | 常规开发，包括新功能、开发阶段的问题修复、文档修改、测试和代码重构 | `feat/user-login`      |
| `hotfix/` | 紧急修复已发布版本中的严重问题                                     | `hotfix/payment-error` |

`feat/` 和 `hotfix/` 是分支类别；`fix`、`docs`、`test`、`refactor` 等是提交类型，两者用途不同。

#### 分支使用规则

1. 常规开发从最新的 `main` 创建 `feat/` 分支，并以模块或任务命名，例如 `feat/user-login`。
2. 功能开发过程中发现的问题修复，以及相关的文档修改、测试和重构，都在对应的 `feat/` 分支内完成；不另外创建 `fix/`、`docs/`、`test/` 或 `refactor/` 分支。
3. 一个 `feat/` 分支应聚焦于同一模块或任务。开发期间及时同步 `main` 的更新；完成后推送分支并创建 PR，不直接向 `main` 推送开发提交。
4. 仅对已发布版本中的紧急问题创建 `hotfix/` 分支。紧急修复从 `main` 创建，通过 PR 审查后合并回 `main`。
5. PR 通过审查并满足项目检查要求后合并。合并完成后删除已合并的远程分支。一般开发流程不需要预先创建 `release` 分支。

### 提交信息

提交标题采用 Conventional Commits 格式：

`<type>[可选的 scope][!]: <description>`

- `type` 使用小写英文，冒号后使用一个空格。
- `scope` 可选，用于说明受影响的模块，例如 `feat(auth): 支持邮箱登录`。
- `description` 使用简洁、明确的动词短语描述本次改动；不以句号结尾。
- `!` 表示该提交包含不兼容变更。

常见的 `type` 如下：

| `type`     | 用途                             |
| :--------- | :------------------------------- |
| `feat`     | 新增功能                         |
| `fix`      | 修复问题                         |
| `docs`     | 修改文档                         |
| `style`    | 不影响代码含义的格式调整         |
| `refactor` | 不新增功能、不修复问题的代码重构 |
| `perf`     | 性能优化                         |
| `test`     | 添加或修改测试                   |
| `build`    | 修改构建系统或外部依赖           |
| `ci`       | 修改持续集成配置                 |
| `chore`    | 其他维护性改动                   |
| `revert`   | 撤销之前的提交                   |

示例：

```plain
feat(auth): 支持邮箱登录
fix(menu): 修复窄屏下菜单溢出
docs: 更新本地开发说明
```

#### 提交正文和脚注

正文用于补充说明改动的背景、实现方式或影响范围；简单改动可以省略。标题与正文之间空一行。

通过 `Closes #issue_hash`、`Fixes #issue_hash` 或 `Resolves #issue_hash` 关联并关闭 Issue。只需关联但不关闭时，使用 `Refs #issue_hash`。

不兼容变更应在标题中使用 `!`，并在正文或脚注中说明影响及迁移方式；脚注以 `BREAKING CHANGE:` 开头，例如：

```plain
feat(api)!: 移除旧版用户查询接口

BREAKING CHANGE: 请改用 GET /api/v2/users。
```

### PR 规范

本项目通过 PR（Pull Request）进行代码审查和合并。

1. 标题应清楚概括改动，可沿用 Conventional Commits 格式。
2. 描述改动目的、主要内容及必要的测试结果；关联 Issue 时使用 `Closes #issue_hash` 等关键字。
3. 提交前确认改动范围合理，并运行与改动相关的检查和测试。
4. PR 应保持聚焦；若包含多个互不相关的改动，应拆分为多个 PR。
5. 至少一名协作者审查通过且自动化检查通过后再合并；未解决的审查意见应先处理或明确答复。
6. 合并时优先使用仓库配置的合并方式，并在合并后删除已合并的开发分支。

## 变量命名规范

chilis采用*中缀-前后缀命名法*~没听过很正常因为是我自创的~

### 基本格式

`<前缀>_<中缀>_<后缀>`
其中中缀只有一个，前缀和后缀可以有多个，彼此用下划线链接

### 中缀规范

中缀应当根据变量的不同用途选择不同的形式

| 用途            | 形式           |
| :-------------- | :------------- |
| 名称            | 名词           |
| 功能函数/纯过程 | 动词原形       |
| 转换方法        | to+新类型      |
| 开关变量        | 动词/名词+able |
| 完成状态标记    | 动词+ed        |
| 进行状态标记    | 动词+ing       |
